OpenClaimFlow

OpenClaimFlow is a working claim processing backend, not a CRUD scaffold: a Spring Boot API over PostgreSQL behind an Angular SPA, with a claim lifecycle — filing, routing, staged assessment, an authority gate, and an append-only audit trail — that runs end to end. This page is the system, from service topology to the exact request path a claim takes.

A running application with real data — not a mock-up.

Demo credentials are available on request — claimant, adjuster, or supervisor roles.

What happens when a claim is filed

  1. The claimant files a first notice of loss at POST /api/claims (multipart: policy number, holder name/email, loss date/location/description, optional covers JSON, photos). The policy must be ACTIVE and holder-matched, or the response is the same 404 shape as a missing policy — no existence signal. A per-claimant rate limit (20 filings / 24h, 429 + Retry-After) is enforced against the fnol_submission ledger.
  2. On receipt the claim number is issued immediately: nextval('claim_number_seq') becomes CLM-000123. A duplicate guard runs before the number is burned — same policy + loss date + cover set (order-insensitive, amounts ignored) within 24h returns the original number as HTTP 409.
  3. The claim is routed and assigned inside the filing transaction. ClaimClassifier maps the product code to a level (L1/L2/L3) from the authority config; ClaimAssigner locks the level's adjusters (SELECT … FOR UPDATE) and LoadBalancer picks the least-loaded qualified adjuster (fewest open claims, lowest id on ties). The claim is never observable as UNASSIGNED; with no eligible adjuster it parks there and logs a warning.
  4. The assigned adjuster works a staged workflow — REVIEW → VERIFICATION → DECISION (orthogonal to status) — via POST /api/claims/{{ '{' }}n{{ '}' }}/review, PUT /api/claims/{{ '{' }}n{{ '}' }}/assessment and per-cover verification records. Server-side guardrails reject an assessed amount above the cover's sub-limit, and send-back parks the claim at NEED_INFO for the claimant.
  5. The authority gate — AuthorityGate, a pure function — compares the proposed amount to the actor's level limit. Inside the limit the claim closes and a payment row is recorded; above it the claim is re-assigned to the least-loaded L2 or moved to ESCALATED_SUPERVISOR. No-self-approval is structural: an escalation always leaves the actor's hands. Denials are never authority-gated.
  6. Every closure carries a ≥20-character rationale, and every REJECTED cover carries one of 7 denial codes (DenialReason: NOT_COVERED, EXCLUDED_PER_CLAUSE, ABOVE_SUB_LIMIT_EXHAUSTED, INSUFFICIENT_EVIDENCE, DUPLICATE_PRE_EXISTING, FRAUD_SUSPECTED_REFERRAL, OTHER). Validation runs before any write — a bad body never moves the claim.
  7. Concurrent edits are detected, not overwritten: claim.version (@Version, V21) makes every money-path write a compare-and-swap, and a stale expectedVersion returns 409. In parallel, AgingScheduler (03:00, tenant timezone) pushes undecided claims 3 days old to L2 and 5 days old to the supervisor; reopening is supervisor-only (POST /api/claims/{{ '{' }}n{{ '}' }}/reopen, version-checked, rationale required).
  8. Every state change appends to audit_log (V7 DB trigger, append-only — no edit or delete endpoint exists). Claimant, assignment and decision emails are transactional outbox rows in email_outbox, written in the same transaction and delivered by a 60-second dispatcher (8 attempts, backoff) so a decision mail is never lost.

Data & identity

One PostgreSQL 16, schema owned by Flyway claims (dev) and claims_e2e (hermetic E2E) behind V1–V30 migrations. Migrations are forward-only and immutable — the audit log has no down-migration.
Keycloak realms and roles scope every surface Realm claims; roles claimant, adjuster_l1, adjuster_l2, adjuster_l3, supervisor map to ROLE_* authorities. The SPA authenticates with OIDC/PKCE (S256), silent check-sso on guarded routes.
404, never 403 Object-level auth lives in ClaimAccess: a claim is visible to the supervisor or its assigned adjuster (JWT subject → staff cache). "May not see" becomes a not-found response, so nothing reveals that a claim number exists.
The claimant visibility wall Claimant DTOs never carry reserves, internal notes, the assignee, deductible, adjustment, verifier or proposals — asserted in tests. On closure a claimant sees per-cover decisions, approved amounts and net payable only.
Evidence is validated and pinned PhotoValidator: count (≤5) → content type (image or PDF) → size (≤10 MB) → magic bytes (PNG/JPEG/GIF/WEBP/PDF); SHA-256 + size recorded per attachment. Storage sits behind PhotoStorage — filesystem default, an S3-compatible seam for prod with no code change.
Privacy and 7-year retention Claimant self-export (GET /api/privacy/me/export, metadata only — never bytes), supervisor anonymisation (overwrites listed columns, leaves the audit log untouched), and a report-only retention view (claims.retention.closed-years=7, no auto-delete).

The AI assistant

Grounded in the claim's own covers and clauses GET /api/claims/{{ '{' }}n{{ '}' }}/policy-clauses returns loss-date-selected wording for the product and the claim's opted covers only; the advisory prompt is built from that, not from free-form retrieval.
Answers that cite, validated server-side AiOutputValidator is strict: the exact cover set, cites restricted to served clause ids, bounded rationale and non-negative payable. A model citing an out-of-scope clause is rejected, never silently trimmed.
Out-of-scope covers excluded before the model sees them Clause scoping happens in the service (PolicyClauseService.forClaim), so covers the claim does not carry never reach the panel or the prompt.
Rules-only fallback, not a failure With DEEPSEEK_API_KEY blank (or a provider error) the client fails closed and CoverageRules serves a deterministic DEGRADED advisory (waiting periods → needs-more-info, sub-limit caps payable, co-pay chains). The outcome is recorded — COMPLETED / DEGRADED / FAILED — and deduped per (claim, version). Advisory only: no decision path branches on it.

Decisions, not just features

A monolith with module boundaries, not microservices One Spring Boot app, packages enforcing the seams; there is no Kafka — event delivery is a transactional email outbox. Documented in docs/decisions.md.
Transactional outbox over fire-and-forget mail Mail rows commit with the claim; a 60s dispatcher retries (8 attempts, backoff). A decision can never be decided without its email being durably queued.
The authority gate is a pure function Exhaustively unit-tested without a database; no-self-approval is structural, not an extra check.
Optimistic locking over silent overwrites @Version + expectedVersion compare-and-swap turn a concurrent edit into a 409 conflict banner (V3 S5 in docs/decisions.md).
Filesystem-first storage with an S3 seam claims.storage.backend flips the bean; zero-dependency SigV4 for S3, object keys portable across backends.
Degrade-honest AI A blank API key is a designed DEGRADED state, never a thrown error; the key is never written to files, logs or audit rows.
